# Шаблон и обновления

Этот репозиторий — шаблон (GitHub template repository). Из него создаются
репозитории под конкретные наборы презентаций, а улучшения инфраструктуры
можно доставлять в уже созданные.

## Как начать новый проект

1. Кнопка **«Use this template»** → «Create a new repository».
2. `pnpm install`
3. Заполнить `shared/project.json` — название, автор, заголовок вкладки.
4. `pnpm slides 01-demo` — посмотреть демо-презентацию: она же справочник
   по разметке.
5. Написать своё, демо удалить: `presentations/01-demo/` целиком.

## Почему обновления не приходят сами

У репозитория, созданного из шаблона, **нет общей истории с шаблоном** —
в отличие от форка там один коммит «Initial commit». Git умеет сливать
только ветки с общим предком, поэтому GitHub не может предложить обновление
автоматически.

Обходится это слиянием с `--allow-unrelated-histories`. Именно его и делает
workflow «Обновление из шаблона» — не магия, а автоматизация ручной операции.

**Первый запуск всегда даёт большой конфликтный PR.** Это свойство механизма,
а не поломка: git впервые сопоставляет два несвязанных дерева. Последующие
обновления выглядят как обычные диффы.

## Как обновиться

Actions → **«Обновление из шаблона»** → Run workflow.

Расписания нет намеренно: синхронизацию стоит запускать тогда, когда есть
время разобрать PR и прогнать `pnpm check` локально. Есть флажок
«Показать изменения, не создавая PR» — полезно посмотреть объём заранее.

После вливания PR выполните `pnpm install`: lock-файл не синхронизируется,
и версии зависимостей могли разойтись.

### Что нужно один раз настроить

Секрет `TEMPLATE_SYNC_TOKEN` — personal access token со scope `workflow`
(и `repo`, если репозиторий приватный). Без него синхронизация упадёт на
файлах `.github/workflows/`: встроенному `GITHUB_TOKEN` не разрешено их менять.

## Что синхронизируется, а что нет

| Синхронизируется | Принадлежит проекту |
| --- | --- |
| `scripts/`, `shared/` (лейауты, компоненты, стили) | `presentations/`, `apps/` |
| конфиги: ESLint, TypeScript, Prettier, cspell | `shared/project.json` |
| `.devcontainer/`, `.vscode/`, `Makefile` | `README.md`, `CLAUDE.md` |
| `AGENTS.md`, `docs/` | `.cspell/project.txt` |
| `.claude/skills/` | `.claude/settings.json`, `pnpm-lock.yaml` |

Точный список исключений — в `.templatesyncignore`.

**Важная деталь.** `.templatesyncignore` действует только на синхронизацию,
но **не** на создание из шаблона: кнопка «Use this template» копирует дерево
целиком и про этот файл не знает. То есть файл в ignore — это «не трогать
после создания», а не «не копировать». Демо-презентация, README и
`project.json` приезжают стартовыми заготовками и дальше живут своей жизнью.

Следствие: если в `.claude/settings.json` шаблона позже появится что-то
важное, уже созданные проекты этого не получат — понадобится ручная правка.
Для настроек проекта это приемлемо; для `.claude/skills/` — нет, поэтому
они синхронизируются.

Сам `.templatesyncignore` синхронизировать нельзя (ограничение action) —
его правки переносятся вручную.

## Стратегия слияния

По умолчанию action использует `--allow-unrelated-histories --squash
--strategy=recursive -X theirs`. Ключевое здесь `-X theirs`: **при конфликте
побеждает версия шаблона**.

Отсюда практическое правило: файл проекта, не попавший в
`.templatesyncignore`, будет перезаписан молча. Проверяйте список перед
первым запуском.

## Если развиваете сам шаблон

- Изменения инфраструктуры уезжают в чужие репозитории, поэтому в шаблоне
  есть CI (`.github/workflows/check.yml`) — он гоняет `pnpm check` на каждый
  push и PR. В производных проектах его можно удалить.
- **Синхронность демо-презентации и шаблона генератора ничем не проверяется.**
  `pnpm test:generator` доказывает, что шаблон собирается, — версия
  с двумя титульными слайдами собиралась бы точно так же. Правки
  в `presentations/01-demo/` и `scripts/new-slides.mjs` вносите парой.
- Курсовая лексика в общих блоках не нужна: `Task` принимает `label`,
  титульный лейаут — `badge`. Значения по умолчанию задаются
  в `shared/project.json`, а не хардкодом в компонентах.
